## 우아한형제들 — 물어보새 (QueryAnswerBird)

- 만든 팀: BADA(Baemin Advanced Data Analytics). 2023년 사내 해커톤에서 시작
- 배경: 사내 설문에서 약 95%가 업무에 데이터를 쓰지만 절반 이상이 SQL과 신뢰할 수 있는 데이터 추출을 어려워함
- 구조
  - Router Supervisor가 질문을 분류해 전용 체인으로 보냄: 쿼리 생성, 쿼리 해설, 문법 검증, 테이블 해설, 로그 테이블 안내, 컬럼·테이블 안내
  - 질문 정제 단계에서 비즈니스 용어를 뽑고, 검색한 테이블 메타데이터·DDL·few-shot 예시를 합쳐 쿼리 생성
- 넣은 데이터
  - 테이블 메타데이터: 용도, 컬럼 설명, 주요 값, 키워드, 자주 쓰는 서비스, 예시 질문
  - DDL: 사내 데이터 카탈로그 API에서 뽑은 메타데이터로 생성
  - 비즈니스 용어 사전: 기존 데이터 거버넌스 조직과 함께 구축
  - 분석가가 쓴 질문–쿼리 예시
- 평가: 공개 벤치마크(Spider, BIRD) 대신 자체 지표와 데이터셋. A/B 환경과 리더보드로 체인을 비교해 매주 상위 체인을 배포. 초기 개발 중 실험 500회 이상
- 운영: 응답 30초~1분. Slack에서 만족·불만족 평가를 받아 캐시와 개선에 반영
- 배운 점: 사용자의 질문 중 상당수가 쿼리 생성이 아니라 "어떤 테이블을 봐야 하나"였고, 그래서 데이터 탐색 기능으로 넓힘

## 토스플레이스 — 판다 (PANDA)

- 작성: Data Analysis Team Leader, Data Analytics Engineer. 분석 조직이 직접 만듦. 기획부터 출시까지 한 달
- 배경: 데이터 요청의 약 70%가 단순 수치 추출
- 초기 실패: 토큰 낭비, 질문마다 달라지는 테이블 선택, 지표 기준 오해('활성 매장 수'), 비효율 쿼리로 Snowflake 비용 증가
- 해결 순서가 핵심: 모델을 고치기 전에 마트를 정비함
  - 표준 마트(SSOT) 정비. 테이블명 `{mart_type}_{domain}_{subject}`, 컬럼명 `{prefix}_{entity}_{attribute}_{suffix}` 규칙. 모든 테이블·컬럼에 설명 작성
  - 용어와 지표 정의를 표준 마트에 연결. 분석가들이 기준 통일
  - 테이블 선택 점수 = 유사도 × 계층 가중치. 테이블명 일치 +3, 설명 연관 +1. SSOT ×4, 검증된 표준 마트 ×3, 도메인 분석 마트 ×2, 원시·로그 ×1
  - dbt tags로 관리되는 테이블만 manifest로 가져옴
- 실행: 테이블 탐색 → 쿼리 실행 → 결과 검증(필요하면 사용자에게 되물음) → 재시도·수정 → 결과. 예외를 코드로 다 짜지 않고 모델이 판단하는 tool loop
- 답변 형식: 결과, 조회 기준(기간·조건·집계 방식), 인사이트
- 권한: 보안 등급에 따라 허용된 범위 안에서만 조회
- 사용: 일주일 만에 팀원 절반이 사용, 메시지 4,000건 이상, 현재 70% 사용
- 목표치: 데이터 커버리지 90% 이상, 답변 정확도 97% 이상. 현재 측정값은 공개하지 않음

토스 본사 관련
- "LLM은 똑똑한데, 왜 우리 회사 일은 모를까"(2026-07): 사내 문서·메신저·코드를 신뢰 상태가 붙은 컨텍스트로 관리하는 Topic 시스템. 출처가 충돌하면 한쪽을 지우지 않고 `disputed`로 표시하고, 근거가 부족하면 `insufficient_evidence`를 정상 결과로 돌려줌
- 채용 공고와 소개 글에서 데이터 자산을 MCP·API로 열고 시맨틱 레이어를 정비한다고 밝힘

## 당근페이 — 브로쿼리 (Broquery)

- 작성: 당근페이 Data Engineer. 2025 AWS Seoul Summit 발표
- 배경: 비개발 직군의 데이터 요청이 개발팀에 의존, 분석 대기 평균 1~3일
- 요구사항 5가지: 접근성, 의도 파악, 대화 문맥, 잘못된 SQL 점검, 정확성
- 구성: Slack, DynamoDB(대화 기록·피드백), Bedrock 에이전트, OpenSearch RAG, 메타데이터 플랫폼, MCP 서버, Redshift, LangGraph
- 흐름
  - 의도 분석 후 분기(일반 질문 / 쿼리 생성)
  - 스키마 링킹: 키워드 + 벡터 하이브리드 검색으로 넓게 찾고, reranker로 거름
  - MCP로 비즈니스 컨텍스트 보강
  - SQL 생성 후 실행 전에 자가 점검으로 오류 수정
  - Redshift 실행, 표·차트와 요약을 Slack으로 응답. 1분 이내
- 메타데이터 세 종류
  - 비즈니스: 용어 정의, 지표, 정책 맥락, 담당자, 개인정보·민감 정보와 접근 정책
  - 기술: ERD, 테이블·컬럼 상세, 샘플 쿼리. dbt YAML에서 자동 추출해 Git으로 관리
  - 운영: 데이터 계보, 배치 로그, 접근 로그
- 눈여겨볼 것
  - 샘플 쿼리(질문–SQL 쌍) 유무에 따라 정확도가 90% 이상 차이. 도메인 전문가가 직접 등록하는 화면을 제공
  - 용어 사전에 정의만이 아니라 집계 조건까지 적음. MAU라면 로그인 기준인지, 특정 OS만인지, 집계 시점은 언제인지
  - ENUM 값 설명은 DB가 아니라 애플리케이션 코드·위키에서 가져와 보강
- 평가: RAGAS, LLM-as-a-judge, 검색 지표와 생성 지표
- 파인튜닝: 샘플 쿼리가 충분히 쌓인 뒤의 계획. 후보 SQL 선택 단계에 Llama·Qwen 지도 학습을 실험 중
- 단점으로 든 것: 모델 커스터마이징 제약, 트래픽 증가 시 비용, 클라우드 의존

## 당근 — 데이터캣과 사내 에이전트 플랫폼

- 사내 채팅 KarrotChat에서 데이터캣과 대화해 SQL과 테이블 구조를 몰라도 데이터를 조회(당근 GenAI 플랫폼 글, 검색 요약 기준)
- LLM Router로 모든 호출을 어느 서비스가 요청했는지 추적
- 기사 기준: 데이터 분석 에이전트가 사내에서 가장 먼저 활성화됐고, Slack에서 에이전트 180개 이상이 동작. 같은 요청의 비용과 품질을 교차 검증해 모델 변경을 제안하는 시스템 운영
- 에이전트 플랫폼 KAMP(2025-11 발표): 노코드로 그래프 구성, 버전·롤백, 로그 디버깅, 주기적 평가
- 평가 방식: 처음에는 사람이 평가하고, LLM의 평가가 사람과 90% 이상 일치하면 그때부터 LLM이 평가

## 공통 설계 원리

1. 품질은 모델보다 컨텍스트가 정한다. 세 회사 모두 테이블·컬럼 설명, 용어 사전, 샘플 쿼리를 먼저 정비했다
2. 정비된 마트가 전제다. 판다는 SSOT에 가중치 4배를 주어 원시 테이블로 새는 것을 막았다
3. 학습(파인튜닝)은 출발점이 아니다. 전부 API 모델 + 검색 + few-shot으로 시작했고, 파인튜닝은 샘플 쿼리가 쌓인 뒤의 다음 단계다
4. 생성한 SQL은 바로 믿지 않는다. 문법 검증, 실행 후 결과 검증, 애매하면 사용자에게 되묻기
5. 답변에 조회 기준을 함께 보여 준다. 기간·조건·집계 방식이 보여야 사용자가 틀린 답을 걸러낸다
6. 평가셋을 자체 구축한다. 공개 벤치마크는 사내 스키마와 용어를 반영하지 못한다
7. 권한은 질의 단계에서 건다. 보안 등급별 조회 범위, 읽기 전용 실행
8. 피드백을 자산으로 쌓는다. 만족·불만족, 검증된 쿼리를 다시 예시로 넣는다
9. 쿼리 생성보다 탐색 수요가 크다. "어느 테이블을 봐야 하나", "이 지표 정의가 뭔가"에 답하는 기능이 함께 필요하다

## 필요한 데이터와 학습

학습 데이터가 아니라 검색해서 프롬프트에 넣을 자료가 필요하다.

- 테이블·컬럼 설명 (dbt YAML 등)
- 지표 정의서: 이름, 산식, 집계 조건, 기준 테이블
- 용어 사전: 표준 명칭, 약어, 동의어
- 검증된 질문–SQL 쌍 수십 개부터
- ENUM·코드 값 설명
- 평가셋: 질문, 정답 SQL, 정답 결과

파인튜닝·LoRA를 고려하는 시점
- 검증된 질문–SQL 쌍이 수천 건 단위로 쌓였을 때
- 비용·지연·망분리 때문에 작은 자체 모델로 옮겨야 할 때
- 그 전에는 검색과 예시 개선이 같은 노력 대비 효과가 크다

## 직접 구현할 때의 구조

```
질문
 → 분류 (지표 조회 / 테이블·정의 탐색 / 일반)
 → 검색 (지표 정의서, 테이블 설명, 유사 질문–SQL)
 → SQL 생성 (검색 결과를 컨텍스트로)
 → 검증 (SELECT만 허용, 문법 확인, LIMIT·스캔량 제한)
 → 실행 (읽기 전용 계정)
 → 결과 확인 (0건·이상치면 재시도 또는 되묻기)
 → 응답 (결과 표·차트, 조회 기준, 사용한 SQL, 해석)
 → 기록 (질문, SQL, 평가)
```

구현 방식 두 가지
- 고정 파이프라인: 단계가 정해져 있어 디버깅과 평가가 쉽다. 물어보새·브로쿼리 방식
- tool loop: 모델에 `search_tables`, `get_metric_definition`, `run_sql` 도구를 주고 스스로 반복하게 한다. 코드가 적고 예외에 강하지만 비용과 실행 시간 통제가 필요하다. 판다 방식

대시보드에 붙일 때 고려할 것
- 대시보드의 현재 필터(기간, 카테고리)를 질문의 컨텍스트로 넘긴다
- 대시보드 카드가 쓰는 쿼리가 곧 검증된 질문–SQL 쌍이다. 이것부터 예시로 넣는다
- 자유 질의보다 "이 카드 수치가 왜 변했나" 같은 카드 단위 질문이 정확도를 잡기 쉽다

## 실무로 이어지는 지점

- 데이터 분석가 채용 공고에 자주 나오는 "표준화된 마트 구축·운영", "데이터 거버넌스", "AI 도구 활용"은 위 원리 1·2와 같은 이야기다. 마트와 지표 정의서를 정비하는 일이 곧 AI 활용의 선행 작업이다
- 판다는 분석 조직이 한 달 만에 만든 사례라, 분석가가 주도할 수 있는 범위라는 근거가 된다
- 제안 순서: 지표 정의서와 대시보드 쿼리 자산화 → 카드 단위 질의 → 자유 질의 → 평가셋으로 정확도 관리
